# SimGameEngine · 01 总体架构与边界

> 状态：架构设计稿（v0.2，2026-11-16）；文中标注【已落盘】的部分可直接使用。
> 前置阅读：`00-INDEX.md`；建议对照 `../Render/doc/01-Overview.md` §1.2「非目标」理解职责切分。

---

## 1. 目标

| 目标 | 说明 |
|---|---|
| 树型节点管理 | 场景内一切对象都挂在唯一一棵树上，父子关系决定变换继承、激活传播、更新顺序 |
| GameObject 概念 | 空壳容器 + 组件集合，对象间不靠继承区分「是什么」，靠挂了什么组件决定（Unity 式组合优于继承） |
| 组件化数据 | Transform / Mesh / Material / Shader / Animation / Effect 均为可插拔组件；Camera / Light / Probe / UI 是同一棵树上的特殊组件组合 |
| 合批提交 | 按 Shader + Material 决定哪些 Mesh 可以合并，写进 RenderObject 后交给 Render；引擎不直接碰图形 API |
| 生命周期 | 统一的 awake / start / update / lateUpdate / fixedUpdate / onEnable / onDisable / dispose 钩子 |
| 碰撞与物理 | 第 11/12 章：Collider 检测重叠、Rigidbody 在固定步长里做轻量积分与接触求解 |
| 画面氛围 | 第 13/14 章：天空盒 / 环境光 + Volume 参数栈，后者依赖 Render 打通 P2 |
| 2D 游戏 | 第 15 章：SpriteRenderer / Tilemap / 排序层，复用 QUAD、动态网格与正交相机 |
| 单语言 | 全部用 SLang（`.sl`）写；渲染后端能力通过现有 `SLangRender` 模块门面调用 |

## 2. 非目标（明确不做）

这几项由 `SLangRender` 负责，本模块不重复实现：

- 图形 API 与后端：GL / D3D11 / Vulkan / GLES 的选择、WGL 离屏上下文、13 阶段管线；
- 剔除 / 排序 / Pass 编排 / UBO 打包 / 后处理的**执行**；
- RenderObject 内部的 GPU 资源句柄管理。

这几项暂不属于 v0.2 范围：

- 完整商业级物理引擎（PhysX 级关节 / 软体 / 布料 / 流体）：v0.2 只做轻量刚体 + 冲量求解；
- 导航、音频、网络（Unity 的 NavMesh / Audio / Netcode 对应物）；
- 完整的资产数据库与序列化（场景存盘 / 热重载待后续章节扩展）；
- 骨骼蒙皮、GPU 粒子、SRP Batcher 式自动合批（Render 05 文档将其列为 M7 不承诺项）。

## 3. 四层架构

```
┌─ L3 应用层 ───────────────────────────────────────────────┐
│  游戏脚本：继承 Behaviour，实现 update / 事件钩子          │
└──────────────────────┬────────────────────────────────────┘
                       │ 读写节点 / 组件
┌─ L2 引擎层（本模块）──▼────────────────────────────────────┐
│  Scene → GameObject 树 → Component / Behaviour             │
│  帧循环驱动 → 变换更新 → 可见性收集 → 合批器                │
│  子模块：Collider / Rigidbody（11/12）、Skybox / Volume     │
│          （13/14）、SpriteRenderer / Tilemap（15）          │
└──────────────────────┬────────────────────────────────────┘
                       │ RenderObject 批次 + Camera + Light + 后处理参数
┌─ L1 渲染门面（Render/SLangRender）▼────────────────────────┐
│  RenderPipeline / RenderObject / Mesh / Material / Shader   │
│  Camera / Light / CommandBuffer / 13 阶段 runStages         │
│  PostProcessPass（亮度/饱和度/暗角，Volume 参数栈未开始）   │
└──────────────────────┬────────────────────────────────────┘
                       │ @DllStaticImport
┌─ L0 原生渲染层 ───────▼────────────────────────────────────┐
│  sl_render_lib.dll（C）：剔除 / 排序 / UBO / 后端 / 回读    │
└─────────────────────────────────────────────────────────────┘
```

**边界契约**：L2 每帧向 L1 交付「批次化的 RenderObject 列表 + 主相机参数 + 灯光槽位 + 后处理参数」，L1 不认识 GameObject；L2 不认识 `slr_*` 原生符号。Render 文档原话：「渲染引擎不持有 GameObject 概念。每帧由宿主把可见候选注入管线」（`01-Overview.md` §1.3），宿主就是本模块。

## 4. 一帧数据流（整合核心）

```
Application.tick(dt)
  │
  ├─ 1. 时间推进 / 输入采样
  ├─ 2. fixedUpdate × N        ← 碰撞检测 + 物理积分（第 11/12 章）
  ├─ 3. Behaviour.update       ← 按树序，父先子后；isEnabled=false 跳过
  ├─ 4. Behaviour.lateUpdate   ← 相机跟随等"等别人更新完"的逻辑
  ├─ 5. 变换刷新               ← 脏节点自顶向下重算 localToWorld（物理写回）
  ├─ 6. 可见性收集             ← activeInHierarchy + layer ∩ cullMask
  ├─ 7. 合批                   ← 键 = shaderProgram + material + meshSlot + layer + queue + 动画/特效状态
  ├─ 8. 同步 RenderObject      ← setPosition/Scale/RotationZ/Color/Material/...（池化复用）
  ├─ 9. 相机 / 灯光 / Volume   ← pipe.setCamera / Light.applyTo / 后处理参数收集（第 14 章）
  ├─10. pipe.renderFrame(t, dstPtr) 或 runStages(t, dstPtr)
  └─11. 帧尾：延迟销毁 dispose，回收 RenderObject 句柄
```

第 7 步是本模块的立身之本：**不同 GameObject 上挂了同一 Shader + 同一 Material 实例的 Mesh，先合并成一次 RenderObject 提交**，而不是一个节点一个 draw。第 8 步的字段写入能力见第 05 章映射表。第 2 步的物理严格跑在固定步长，不随渲染帧率变化（第 09/12 章）。

## 5. Unity 概念对照（口径统一）

| Unity 概念 | 本模块做法 | 差异说明 |
|---|---|---|
| GameObject + Transform（必带） | GameObject 创建时强制挂一个 Transform | 不允许无 Transform 的节点 |
| Component 组合 | `addComponent / getComponent / removeComponent` | 同类组件唯一，不重复挂载 |
| MonoBehaviour 生命周期 | `Behaviour` 已落盘完整钩子集合 | 钩子名与 Unity 对齐（含 `lateUpdate` / `fixedUpdate`） |
| Layer + SortingLayer + renderQueue | 节点 `layer` + Renderer `queue` | RenderObject 已有 `setLayer/setQueue`，相机用 `cullMask` 收 |
| MeshRenderer 提交绘制 | 合批器统一提交；`Renderer.render()` 当前恒返回 false | Unity 里 Renderer 自己画，这里**不**，见第 04 章 |
| Material + Shader 决定合批 | 合批键取自 `Material.resolveProgram()` 与材质实例 | 对齐 SRP Batcher 思路，但本模块做 CPU 侧批次组织 |
| Camera / Light 作为组件 | 挂在 GameObject 上，随父节点 Transform 移动 | Render 侧 `Camera`/`Light` 已是 Component 子类 |
| ReflectionProbe / LightProbe | Probe 组件（设计稿） | Render 侧暂无对应能力，先留数据结构 |
| Canvas / UI | `UIBehaviour` + `RectTransform`，走 QUAD 批次 | `RectTransform.sl` 现位于 Render 模块，依赖待建 |
| Animator / ParticleSystem | Animation / Effect 组件（设计稿） | 简单效果走 Render 的 `setAnimated(mode,speed)` |
| Collider / Rigidbody | 第 11/12 章 | 轻量自研；不接 PhysX，关节 / 软体不在范围 |
| Skybox / Lighting Settings | 第 13 章 | Render 有 `setAmbient`；cubemap 天空盒链路未打通 |
| Volume / VolumeProfile | 第 14 章 | Render 的 P2 参数栈「未开始」，当前只有三个全局后处理数 |
| SpriteRenderer / Tilemap / SortingLayer | 第 15 章 | 复用 MESH_QUAD + uploadMesh + 正交 setCamera |

## 7. 依赖与接入（速览）

RenderTest 已验证可用的组合（第 10 章展开）：

- 模块引用：`SLangQT 0.1.0` + `SLangRender 1.0.0` + `Core` / `Std` / `Math`；
- 纹理另需 `SLangImage 1.0.0`（`import SLangImage;`）；
- 源码：`import SLangRender;`（QT 显示另 `import SLangQT;`），`Float32_3/4x4` 由 `import Math;` 提供，`Component` 由 `import Std;` 提供；
- 原生库 `sl_render_lib.dll` 必须与 module.json 同目录；**后端切换后管线 / 纹理句柄全部失效，需要全量重建场景**（`RenderTest.sl` 与 `Render/doc/13` 均有证据）。

## 8. 设计决策记录

| 编号 | 决策 | 理由 |
|---|---|---|
| D1 | 合批放在引擎层，不塞进 Render | Render 定位为纯渲染引擎，明确不接收 GameObject；批次作为「可见候选」注入最自然 |
| D2 | 节点激活态向子树传播 | 与 Unity `SetActive(false)` 语义一致；禁用父节点整棵子树不更新、不渲染 |
| D3 | 一个 GameObject 同类组件唯一 | 避免合批时同名组件多实例导致语义含糊；需要多个实例就建子节点 |
| D4 | 动画先走 `setAnimated` 内置模式，自定义采样后接 | Render 已有可用模式；骨骼 / 蒙皮超出 v0.1 |
| D5 | UI 走 2D QUAD 批次，不进 3D 合批 | 与 Render 的 UI 非目标一致（Render 只提供 2D 绘制路径） |
| D6 | 文档只描述引擎自身架构与 API，不写 C VM / Front 内部 | 读者是写 SL 游戏逻辑的人，不是改编译器的人 |
| D7 | 碰撞检测与物理响应拆成两章（11/12） | 检测可独立用于拾取 / 触发器，响应依赖固定步长；两者职责不同 |
| D8 | 物理只做轻量自研，不接第三方引擎 | 保持单语言与低依赖；关节 / 软体等超出 v0.2 范围 |
| D9 | Volume 先定义参数栈契约，等 Render P2 落地再接 | Render 明确「未开始」；提前定义可避免引擎侧接口反复改动 |
| D10 | 2D 复用 QUAD + 正交 setCamera，不新建 2D 后端 | Render 已有 MESH_QUAD / uploadMesh / l,r,b,t 相机参数，够用 |
| D11 | Unity 数据不硬解原生格式，自建导出器出独立 JSON | Scene/Prefab/Material 是 YAML+GUID 引用、Shader 不可翻译；Editor C# 导出器可直接调运行时 API，格式自控且未来可换任意 DCC |
| D12 | FBX 走离线转换器（ufbx 起步）汇入同一 schema；资产 shader 用通用 HLSL 源 | 运行时不背 FBX 依赖；HLSL 是 Render 既定源格式（d3d11 直编 / vk 经 DXC 转 SPIR-V 规划），固化 5 效果做降级兜底 |
