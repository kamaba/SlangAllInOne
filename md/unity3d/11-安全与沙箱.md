# 11 · 安全与沙箱（可选）

> 热更代码来自「可远程下发」的 slb，**默认不应拥有与本地代码同等的系统权限**。
> 本文件设计热更代码的沙箱/白名单/完整性策略（本期为可选增强，起步可简化）。

---

## 1. 威胁模型

| 威胁 | 说明 |
|------|------|
| 恶意/被篡改的热更包 | 远程 slb 被中间人替换，注入非法逻辑 |
| 越权系统调用 | SL 经 systemCall 调到不应开放的系统方法（文件/进程/网络） |
| 资源耗尽 | 热更脚本死循环 / 狂分配，拖垮游戏帧 |

---

## 2. 完整性（防篡改）

- 远程 slb **签名校验**：下发方用私钥签名，Unity 侧用公钥验签后才装载（`09` §5 下载链路）。
- 复用 SLB 既有校验：`SLB_DESIGN.md` §1.2 已有 magic + 版本门 + 段表边界 + CRC32 + 可选 SHA-256 摘要 + `verify` 命令 → 先 `verify` 再装载。
- 模块 uuid 比对（`SLB_DESIGN.md` §4.6），防止张冠李戴。

---

## 3. 系统方法白名单（R7 关联）

SL 调系统方法走 `systemCalls[]`（`Core.jsonc`，R7）。沙箱思路：
- **热更模块只暴露「游戏逻辑」systemCall 子集**（Unity 绑定层 `05` 的 `SystemUnity.*`），**不暴露** 文件/进程/FFI 等高风险能力（`PROCESS_DESIGN.md` / `ffi-design.md`）。
- 装载期按「模块来源」决定 capability 集：本地随包 slb = 全量；远程 slb = 受限白名单。
- 类比 `PLUGIN_SYSTEM_DESIGN.md` 的 `fallback: error|disable` 降级策略——未知/未授权 capability 直接拒。

---

## 4. 执行隔离（isolate）

C VM 已有 isolate（1:1 OS 线程真并行，`vm_isolate.h`）。沙箱可：
- 每个热更模块跑在独立 isolate，互不可见内存；崩溃/越界限定在自身域（不拖垮宿主）。
- 资源配额：监控 isolate 的分配/帧时间，超阈熔断（重载旧域 / 停用该模块）。

---

## 5. 资源与帧率守护

- 热更逻辑在 `Update` 里跑（`06`），桥接层加「单帧预算」：SL 执行超时则中断 + 告警，防卡死。
- C VM 的 GC（`GC_DESIGN.md`）手动内存 + 引用计数，需确认热更频繁装载/卸载 isolate 不泄漏（host 句柄表随域清理，`05` §6）。

---

## 6. 与 Unity 安全模型的关系

- Unity 原生插件本身有平台级签名/权限（尤其 iOS 应用沙箱）。
- SL 热更脚本的权限**不超过** 宿主 C# 已拥有的权限——它只能调 Unity 已暴露的 API（`05`），不能凭空提权。
- 真正风险点是「宿主 C# 暴露了过宽桥」，故白名单在**桥接层**收口最稳。

---

## 7. 验收清单（本步交付判据，可选）

- [ ] 篡改的 slb 被签名校验/verify 拒绝装载。
- [ ] 远程模块调文件/进程类 systemCall 被白名单拒绝。
- [ ] 某热更模块崩溃限定在自身 isolate，宿主不崩。
- [ ] 超帧预算的 SL 逻辑被熔断告警。
