## 1. 用户约束与最终选型

用户定稿：**「尽量使用 C++ 绑定，而不是使用 C# 的逻辑绑定，直接 SLang 调用 C++」**。

因此放弃 `05-脚本绑定与Unity API映射.md` §2.1 的起步方案（systemCall 直桥 → Unity C# host function table），
采用 §2.2 **FFI 直调**：SL 源码用 `@DllImport` 声明式绑定，装配期由 C VM 改写为 `CallFFIStatic(77)`，
运行期零 SL 帧直调 C++ 原生插件导出的 `slu_*` 函数。

| 设计稿 | 本次落地 |
|---|---|
| `03` C# `SlangUnityBridge` 调 `cli_run_module_in_memory` | C++ 插件 `slu_boot()` 内部加载 `csimple_lang_dll.dll` 并调 `cli_run_module_in_memory_binary`；C# 完全不接触 C VM API |
| `05` §2.1 `SystemUnity.*` systemCall + R7 四处同步 | `05` §2.2 FFI 直调；**没有新增任何系统方法、没有改 Core.jsonc / Front 枚举 / C VM 源码**（R7 不触发） |
| `05` §4 host function table 把 Unity API 注册进 VM | 不注册；SL 只调 C++，C++ 内部维护 POD 状态 |
| `06` Unity 生命周期 → host 回调 → SL | C# `Update()` 调 `slu_step(dt)`；C++ 推进状态；C# 把状态应用到 Transform |
| `04` SLB mtime 热更 | C# 每 0.5s 比较 `File.GetLastWriteTimeUtc`，变化即重新 `slu_boot`（重跑 SL 模块） |
| `08` IL2CPP/iOS 关 JIT | `slu_boot` 内 `_putenv_s("SL_JIT","0")`；C VM 走解释执行 |
| `02` 平台目录 | 本次只落 `Assets/Plugins/x86_64/`（Windows x64），与 `lib\windows\` 约定同构 |

C# 侧只剩「启动 / 帧驱动 / 状态搬运 / 日志转印」，没有任何逐 API 映射逻辑，符合用户约束。

## 2. 调用链

```
Unity Editor (进程内)
 ├─ C# SlangUnityDriver.Start()  ──P/Invoke──> slu_boot(slbPath)
 │                                                │ C++ 插件 slang_unity.dll
 │                                                ├─ LoadLibrary(csimple_lang_dll.dll)
 │                                                ├─ cli_run_module_in_memory_binary(slb bytes, base_dir, flags)
 │                                                │        │ C VM 装配 SLB
 │                                                │        └─ SL _main_ 执行
 │                                                │              └─ @DllImport("slang_unity", "slu_*")
 │                                                │                    └─ 直调同一 DLL 的 C++ 导出（零 SL 帧）
 │                                                └─ 状态写入 .slushare POD
 ├─ C# Update() ──P/Invoke──> slu_step(dt) / slu_get_state(out9) / slu_pop_log()
 └─ transform.position / eulerAngles / material.color  <- C++ 状态
```

关键：**C# 与 SL FFI 加载的是同一个 DLL 文件**（`Assets/Plugins/x86_64/slang_unity.dll`，
由 `HelloCube.jsonc` 的 `dllImports.path` 绝对路径指定），所以 native 状态天然共享；
`.slushare` 共享数据段只是额外兜底（同一进程内万一被按两个路径加载两次）。

## 4. C++ 绑定面

宿主面（C# / 验证脚本）：

| 导出 | 签名 | 说明 |
|---|---|---|
| `slu_boot` | `const char* -> int` | 读 SLB 字节 → 加载 C VM → `cli_run_module_in_memory_binary`，flags = `NO_BANNER\|QUIET\|FORCE_RUN` (0x0B)，`base_dir` = SLB 所在目录 |
| `slu_step` | `double -> int` | 推进一帧（dt 钳制 0~0.25），返回累计帧数 |
| `slu_get_state` | `double* -> int` | 写出 9 个 double：pos xyz / rot xyz / color rgb |
| `slu_pop_log` | `char*,int -> int` | 环形日志出队（UTF-8） |
| `slu_frame_count` / `slu_last_run_code` / `slu_reset` / `slu_version` | — | 诊断与复位 |

SL 面（`@DllImport` 直调）：

`slu_probe` (`->i32`)、`slu_log` (`utf8->i32`)、`slu_bind_target` (`utf8->i32`)、
`slu_set_spin` (`f64->i32`)、`slu_set_color` (`f64,f64,f64->i32`)、
`slu_set_bob` (`f64,f64->i32`)、`slu_set_base_position` (`f64,f64,f64->i32`)、
`slu_target` (`->utf8`)、`slu_add_tag` (`utf8->i32`)。

`slu_probe()` 返回常量 `20261109`，SL 用它区分「C++ 直调成功」与「FFI 绑定失败 → 静默走 fallback」。

状态结构 `SlUState` 是纯 POD（double / int / 定长 char 数组 / HMODULE），放
`#pragma section(".slushare", read, write, shared)`，`InterlockedCompareExchange` 自旋锁保护；
日志既进环形队列，也 `OutputDebugStringA` + `fputs(stdout)`，所以 CLI 与 Unity Console 两边都能看到。

## 5. 编译与部署要点

- C++：`cl.exe /nologo /W3 /O2 /MD /EHsc /LD /D_CRT_SECURE_NO_WARNINGS /link /SECTION:.slushare,RWS`，
  通过 `vcvars64.bat` 初始化环境（VS 18 / MSVC 14.51）。`/Fo` 必须写**完整 obj 文件名**，
  写目录形式 `C:\dir\"` 会因 cmd 引号转义吞掉后面的源文件参数（实测 `D8003 缺少源文件名`）。
- SL：`slang.exe compile <工程> --format binary+json --no-banner`（R15），产物落
  `SlangAllInOne/out/export/HelloCube/`，再拷进 `StreamingAssets/Slang/`。
- 引用：`HelloCube.jsonc` 写 `./lib/Core.module.slb` / `./lib/Std.module.slb`（Front 编译期走官方库直查），
  Unity 运行期 `base_dir` 指向 `StreamingAssets/Slang`，所以必须把两份 slb 拷到该目录的 `lib/` 下。
- FFI 路径：`dllImports` 里配 `"static": "slang_unity"` + 绝对路径，C VM 装配期预载并按绝对路径解析；
  这样 `slang.exe run`（CWD = Unity 工程根）与 Unity Editor 内 `slu_boot` 都命中同一个 DLL。
- SL 语法坑：注释是 `#`，写 `//` 会在 File 层报 `Lex: /` / `Lex: -`（本次第一轮编译即踩中）。
- Unity C# 坑：`FindObjectOfType` 在 2023.2 已过时（CS0618），改用 `FindFirstObjectByType`。

## 7. 已知坑 / 决策记录

1. **Unity 自动刷新**：编辑器在后台时不会立刻导入新文件；实测 `AppActivate(进程ID)` 或向窗口发 `Ctrl+R` 可触发资源刷新与脚本编译。`[InitializeOnLoad]` 只在域重载时跑，所以冒烟脚本改为 `EditorApplication.update` 轮询 flag，避免「flag 创建时静态构造已执行过」的时序问题。
2. **DLL 占用**：Unity 加载 `slang_unity.dll` 后无法覆盖。热更必须 `-SlOnly`（跳过原生编译与拷贝）；改 C++ 需先退出 Play Mode / 关闭编辑器。
3. **每帧逻辑归属**：`cli_run_module_in_memory_binary` 是同步执行 `_main_` 后返回，VM 实例不常驻。若要在 `Update()` 里跑 SL 帧函数，需要长驻 VM（专用线程 + 条件变量，或 FFI 回调 + VM 生命周期管理），且要处理 Unity 主线程约束。本版把逐帧数值推进放在 C++，SL 负责配置，是最稳的最小闭环；列为后续演进项。
4. **FFI 契约**：本次未放 `slang_unity.dll.slffi.json`，因此编译期不做签名校验；sig 全部手写。后续可补契约并用 `slang ffi-check` 卡 CI。
5. **版本**：本实例不动本体/插件/包版本锚点（R17 各自独立）；新增目录与构建脚本不改 C VM / Front 源码。
6. **R7 未触发**：没有新增 systemCall，所以 `.sl` 声明 / `Core.jsonc` / C VM `.c` / Front `ESystemMethodCall` 四处同步均不涉及。
7. **范围**：仅 Windows x64 + Editor/Standalone；`10-跨平台与部署.md` 的 macOS/iOS/Android/WebGL 清单仍是待办；`07` 的 SLDP 调试、`11` 的沙箱、`05` §2.3 的 `UnityBehaviour` 代理桥未做。

## 9 · v2 升级（同日 · 用户追加要求）

用户追加：**尽量直接调 Unity 引擎层 C++；实在调不了就用最省消耗、最快的方式；最后做成 C# Unity 插件包**。

### 9.1 先证伪「直调引擎对象层」

本机实测（MSVC `dumpbin /exports`）：

| 目标 | 导出 |
|---|---|
| `UnityPlayer.dll`（Standalone 引擎本体） | 仅 `UnityMain` |
| `Unity.exe`（Editor 引擎本体） | 仅 `D3D12SDKPath` / `D3D12SDKVersion`（D3D12 Agility SDK 变量） |
| `Editor\Data\PluginAPI\` | 13 个头文件：`IUnityGraphics{D3D11,D3D12,Metal,Vulkan}`、`IUnityRenderingExtensions`、`IUnityEventQueue`、`IUnityLog`、`IUnityMemoryManager`、`IUnityProfiler(+Callbacks)`、`IUnityShaderCompilerAccess`、`IUnityInterface` |

**Unity 不导出 GameObject/Transform/Component/场景图的 C ABI**，这些入口只在托管层（Mono/IL2CPP）；
内部 C++ 函数未导出、无 ABI 稳定性、Editor/Player 布局不同，逆向调用不可取。
所以「对象层纯 C++」做不到；能直调的是**引擎底层接口**（图形/日志/Profiler/渲染扩展）。

### 9.2 落地形态：UPM 包 `com.slang.unity`

包目录 `<UnityProject>/Packages/com.slang.unity/`（embedded package，无需改 manifest）：
`package.json`（unity 2022.3、samples）、`Runtime/SlangUnity.Runtime.asmdef`（`allowUnsafeCode: true`）、
`Runtime/{SlangUnityNative.cs,SlangUnityDriver.cs}`、`Editor/SlangUnity.Editor.asmdef` + `SlangUnityEditor.cs`、
`Plugins/x86_64/`（3 个 DLL）、`Samples~/HelloCube/`、包内 `README.md`。
工作区真源 = `SlangAllInOne/unity/package/com.slang.unity/`，由 `build-unity-package.ps1` 同步。

原生插件改名 `slang_unity_native.dll`（与 v1 的 `slang_unity.dll` 区分，避免 Unity 进程里同名冲突）；
`HelloCube.jsonc` 的 `dllImports.path` 指向包内绝对路径，C# `DllImport("slang_unity_native")` 与 SL FFI 命中同一份 DLL。

### 9.3 C++ 直连引擎 + 每帧一次跨边界

| 变更 | 内容 |
|---|---|
| `UnityPluginLoad/Unload` | 拿 `IUnityLog`（日志直进 Unity Console，C# 不再转印）、`IUnityGraphics`（`GetRenderer` + 注册设备事件回调）、`IUnityGraphicsD3D11`（`GetDevice` 在渲染线程取） |
| 渲染回调 | 导出 `slu_get_render_event_func()`，C# 用 `CommandBuffer.IssuePluginEvent` **一次性**注册到 `AfterForwardOpaque`，之后引擎每帧在渲染线程直接调 C++ |
| `slu_frame(dt, out9)` | 帧推进 + 9 个 double 状态 + 每 30 帧一次的 SLB mtime 检查，合并为**每帧唯一一次 P/Invoke**；返回 `0x01 热更 / 0x02 颜色脏 / 0x04 已装载 / 0x08 引擎日志已挂载` |
| C# 写入 | `Transform.SetPositionAndRotation` 一次调用；颜色仅在脏标志时用 `MaterialPropertyBlock` 写（`_Color` + `_BaseColor` 兼容 Built-in/URP） |
| `slu_diag(out6)` | 引擎接口挂载、渲染器、D3D11 设备、渲染回调次数、原生帧数、设备事件数 |

`out9` 用 `fixed (double* p)` 传原始指针，零封送复制；C# 侧每帧只做 1 次原生调用 + 1 次引擎写入 + 0 次日志转发。

### 9.4 跨进程共享段陷阱（已修）

`.slushare` 共享段会让**同一 DLL 路径**的多个进程（Unity Editor 与 CLI 验证）看到同一份数据。
其中 `IUnityLog*`、`IUnityGraphicsD3D11*`、`HMODULE vmDll` 是 Unity 进程地址空间内的指针，
外部进程若解引用会崩溃。修复：共享段加 `ownerPid`，`UnityPluginLoad` 写入 PID，
`slu_engine_owned()` 保护日志调用、VM DLL 缓存、渲染回调、diag/flags 判定；
验证脚本也不再调 `slu_reset()`，避免清掉 Unity 进程的引擎绑定。

### 9.6 编译/工程坑（v2 新增）

1. MSVC `/I` 必须写 `/I"path"`，写成 `/I:"path"` 会静默找不到头文件（首轮编译报错）。
2. PowerShell 把带空格的 `/I` 参数传给 `cmd.exe /c` 会破坏引号；改为固定 `build-native.cmd` 批处理，
   并把 Unity 官方 PluginAPI 头文件随源码自包含到 `native/UnityPluginAPI/`（含 `LICENSE.md`），编译路径无空格、包可移植。
3. Unity 头文件含 UTF-8 的 © 注释，MSVC 默认 ANSI 读会报 C4819 → 加 `/utf-8`。
4. `InterlockedIncrement` 目标必须是 `volatile LONG`（`gfxEvents` 原为 `int`，编译报错）。
5. Unity 运行时包内 DLL 被锁，覆盖会失败 → 构建脚本支持 `-SlOnly`（跳过原生编译与拷贝）；
   v1 遗留 `Assets/Plugins/x86_64/` 因旧 DLL 仍被加载删不掉（与新 DLL 不同名，无功能影响），
   关闭编辑器后可手动删除。
6. `CameraEvent.AfterForwardOpaque` 由 CommandBuffer 触发；自定义渲染管线若不触发，需要换事件点
   （`Report` 中 `renderEventCount` 为 0 即说明）。
7. 旧 v1 C# 驱动/冒烟脚本已被构建脚本移除，改由包内 `Editor/SlangUnityEditor.cs` 的
   `Logs/slang-unity-cmd.flag` 轮询（verify / play / report / export）驱动自动化验证。
   删除旧 `Assets/SlangUnity/` 时 Unity 曾报一次 `CS2001`（编译缓存仍引用旧 .cs），刷新后消失；
   随后 Editor verify 重新生成 `RESULT=PASS`，当前脚本编译干净。
8. IDE 的 clang 静态诊断会对 `native/slang_unity.cpp` 报「找不到 IUnityInterface.h / unknown type / void 不完整」等
   **环境性误报**：clangd 未配置 `native/UnityPluginAPI` include 路径，且不认识 MSVC 的
   `__declspec(dllexport)` 与 `#pragma section(...,shared)`。权威编译链是 `build-native.cmd`（MSVC cl.exe），
   实测零错误、导出符号齐全、Unity 内运行 PASS，不要按 clang 诊断改代码。
9. `.unitypackage` 导出实测成功（2.9 MB，GUID/asset/meta/pathname 结构）；Unity 会忽略 `Samples~`，
   所以该格式只含包本体，示例 SLB 需手动放到 `StreamingAssets/Slang/`，UPM 安装则可用菜单一键安装。
