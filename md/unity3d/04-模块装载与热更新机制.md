# 04 · 模块装载与热更新机制（热更核心）

> **热更新 = SLB 二进制包 + 「读取优先 SLB」的 mtime 新鲜度守卫**（`csimple_lang/md/design/SLB_DESIGN.md` §7.4）。
> 本文件设计 Unity 侧如何「监测变更 → 重编译/重装载 → 新逻辑生效」的闭环。

---

## 1. 热更的物理基础：SLB + mtime 守卫

`SLB_DESIGN.md` §7.4 已定义：

| 项 | 规则 |
|----|------|
| 偏好缺省 | **开**（`s_prefer_slb=1`），打开 `*.module.json` 前探测同名 `*.module.slb` |
| 行为 | 存在且新鲜则改读 SLB（日志 `SLB preferred over json`） |
| 新鲜度守卫 | slb 比 json 旧出 **2s 容差**即视为陈旧、回落 JSON（日志 `Stale sibling SLB skipped`） |
| 关闭条件 | ① `--debug` ② `--force-json` |

**这天然就是热更触发点**：前端把 `.sl` 重编译为新的 `*.module.slb`（mtime 更新），
VM 下次装载自动采用新包。我们只需在 Unity 侧「感知 mtime 变化并触发重新装载」。

> R15（AGENTS）：凡"编译模块供运行"一律 `--format binary+json`（slb 主产物 + json 调试副本）。
> Unity 侧导出/装载遵循同一约定。

---

## 2. 两条热更链路

### 2.1 磁盘 SLB 重装载（包内运行 / 真热更）
```
[开发] 改 .sl → Front 编译 → 新 MyHot.module.slb (mtime 新)
[运行] Unity FileWatcher 收到 MyHot.module.slb 变更事件
   → SlangModuleLoader 重新 cli_run_module_in_memory(新包) 
     或走磁盘装载（VM 读新 slb，mtime 守卫自然命中）
   → 新逻辑对后续帧生效
```
- 适合：打包后运行、或 Editor 下改完即热刷。
- 关键点：**不要每帧轮询**，用文件系统监听（`FileSystemWatcher` / Unity `Assets` 导入回调）。

### 2.2 内存 JSON 直传（Editor 零落盘热写）
```
[开发] Editor 内改 .sl → 调 Front 编译 → 内存 JSON 文本
   → cli_run_module_in_memory(json_text, base_dir, flags, args)
```
- 复用 `cli.md` 宿主 API；与 `slang <工程>` 内存链路同源（`SLB_DESIGN.md` §7.1 memory 态）。
- 适合：Editor 内「保存即热更」，不落盘、不污染 StreamingAssets。

## 3. Unity 侧文件监视策略

| 场景 | 监视方式 | 触发动作 |
|------|----------|----------|
| Editor 下 `.sl`/`.slb` 在 `Assets` | `AssetPostprocessor` / `AssetDatabase` 导入事件 | 重新编译 + 内存直传 / 重装载 |
| 运行期 StreamingAssets 内 slb | `FileSystemWatcher`（独立线程）→ 主线程 `UnitySynchronizationContext` 派发 | 重装载 |
| 真机热更（远程下载 slb） | 下载完成回调 | 写盘 + 重装载 |

> 跨线程注意：文件事件在线程池，Unity API 只能在主线程调 → 必须用 `UnitySynchronizationContext` / `MainThreadDispatcher` 把「重装载」派发回主线程（见 `03` §3、`06` §4）。

## 4. 热重载的状态策略（关键设计决策）

热重载**替换的是「执行逻辑」，不是「Unity 对象」**。两种策略：

### 4.1 整模块替换（简单、推荐起步）
- 每次热更：销毁旧 SL 执行域（isolate），新建一个，重跑 `_main_` / 注册回调。
- Unity 侧的 GameObject/Component **不重建**，仅把新的 SL 回调重新挂到 `SlangLifecycle`（`06`）。
- 优点：实现简单、无状态迁移难题。缺点：SL 侧静态/全局状态丢失。

### 4.2 状态保留（进阶）
- 把 SL 侧需要跨热更保留的状态显式序列化（SL 对象 → JSON / 宿主句柄），热更后回填。
- 可借 C VM 的 `global slot`（`csimple_lang/md/design/GLOBAL_SLOT_DESIGN.md`）或宿主侧字典缓存。
- 风险：类型/字段变更导致回填失败 → 需版本化 + 兼容策略。本期**列为待办**（`13`）。

> 建议起步选 4.1，把「热更粒度」控制在「逻辑替换」而非「对象重建」，规避 Unity 序列化陷阱。

## 5. 版本与一致性

- **模块 uuid**（`SLB_DESIGN.md` §4.6）：每个 SLB 带确定性 uuid（`SHA256(模块名)` 前 16 字节）。
- Unity 侧热更时应校验 uuid / 版本号，避免「旧 slb 残留 + 新 json」错位（2s 容差已吸收 slb 先写、json 后写，但仍建议热更时先写 json 再写 slb，或显式 `--force-json` 过渡）。
- **R17 四端版本统一**：SlangUnity 插件自身版本随全仓 `0.0.59` 同步 +1；热更包可由 SLIR 包版本段承载兼容性。

## 6. 与「读取优先 SLB」的排障

| 现象 | 原因 | 处置 |
|------|------|------|
| 热更后仍是旧逻辑 | slb 比 json 旧 >2s（陈旧回落） | 确保先写 slb 且 mtime 新；或 `--force-json` 过渡 |
| 排障要看明文 | SLB 二进制不可读 | `SLB_DESIGN.md`：用 `--debug` / `--force-json` 走 JSON 通道 |
| 引用包没热更 | moduleReferences 递归装载也走偏好 | 引用包同样重编译 + 新 slb |
